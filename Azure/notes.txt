what is cosmos container
A Cosmos container in Azure Cosmos DB is the fundamental unit where your data is stored, partitioned, and scaled. It defines how items are organized, how throughput is provisioned, and how queries are executed.

🔑 What is a Cosmos Container?
Data storage unit: A container holds JSON documents (NoSQL), rows (Cassandra), graph nodes/edges (Gremlin), or tables (Table API), depending on the API you use.

Partitioning: Each container requires a partition key (e.g., /userId), which determines how data is distributed across physical partitions for scalability.

Throughput: You can assign Request Units per second (RU/s) to a container, either fixed or autoscale, to control performance and cost.

Unlimited scale: Containers automatically scale horizontally by adding partitions as data or throughput grows.

📂 Hierarchy in Cosmos DB
Element	Role	Example
Account	Top-level resource with global distribution, consistency, and security settings	mycosmosdb
Database	Logical grouping of containers	CustomerDB
Container	Stores items, defines partition key & throughput	Orders
Item	Individual record (JSON doc, row, node, etc.)	{ "orderId": 123, "amount": 50 }


⚙️ Key Features of Containers
Partition key: Critical for performance; choose a key with high cardinality and even distribution.

Provisioned throughput: Assign RU/s to a single container or share across multiple containers in a database.

Global distribution: Containers replicate across regions automatically when enabled.

Consistency levels: Queries respect the account’s consistency model (Strong, Bounded Staleness, Session, Consistent Prefix, Eventual).

🚀 Example: Creating a Container
Using Azure CLI:

bash
az cosmosdb sql container create \
  --account-name mycosmosdb \
  --database-name CustomerDB \
  --name Orders \
  --partition-key-path "/orderId" \
  --throughput 1000
This creates a container named Orders, partitioned by orderId, with 1000 RU/s throughput. 

⚠️ Common Pitfalls
Poor partition key choice → Leads to uneven load and throttling.

Overprovisioning throughput → Wastes cost if workload is small.

Case-sensitive naming issues → Avoid containers with same name but different casing.

Sensitive info in names → Never include secrets or identifiers in container names.

🔑 What is a Partition Key?
Partition key is not a separate field automatically created by Cosmos DB.

It is an existing property in each item (record/document) that you designate when creating the container.

Cosmos DB uses the value of this property to decide which logical partition the item belongs to.

📂 Example
Suppose you have a container called Orders with documents like:

json
{
  "orderId": "123",
  "customerId": "C001",
  "amount": 50,
  "region": "EU"
}
If you set the partition key path to /customerId, then:

The value "C001" is the partition key value for this document.

All documents with the same customerId go into the same logical partition.

Cosmos DB distributes partitions across physical servers for scalability.

⚙️ Key Points
Partition key path: Defined at container creation (e.g., /customerId).

Partition key value: Comes from the actual property in each record (e.g., "C001").

High cardinality: Best practice is to choose a key with many possible values to avoid hotspots.

Immutable choice: Once set, you cannot change the partition key path for a container.

🚀 Analogy
Think of a partition key like the address on a letter:

The address field (partition key path) tells the postal system where to look.

The actual address value (partition key value in each record) decides which mailbox (partition) it goes into.

Cosmos DB does not require you to manually hash the partition key — it handles that internally. Let me break it down clearly:

🔑 How Partition Keys Work
Partition key path: You define this once when creating the container (e.g., /customerId).

Partition key value: Each item (record/document) must include this property. Cosmos DB reads the value and decides where to place the item.

Automatic hashing: Cosmos DB internally hashes the partition key value to map it to a physical partition. You don’t see or control the hash — it’s managed by the system.

📂 Example
Container: Orders with partition key path /customerId.

Documents:

json
{ "orderId": "1", "customerId": "C001", "amount": 50 }
{ "orderId": "2", "customerId": "C001", "amount": 75 }
{ "orderId": "3", "customerId": "C002", "amount": 20 }
Both items with "customerId": "C001" will be hashed to the same logical partition.

Items with "customerId": "C002" go to a different partition.

Cosmos DB distributes logical partitions across physical partitions automatically.

⚙️ Key Clarifications
You must use the same partition key path for all items in a container.

Items with the same partition key value always end up in the same logical partition.

Cosmos DB hashes values internally to balance load across physical partitions — you don’t need to worry about the hashing algorithm.

Queries and transactions can only span items within the same partition key value efficiently.

So in short:

You define the partition key path once.

Each record must have that property.

Cosmos DB auto-hashes the values to distribute them, but items with the same value always map to the same logical partition.



what is primary key in cosmos db

is this mean different table for each partition
No — a partition in Azure Table Storage is not a separate table. All partitions live inside the same table, but they are logical groupings of entities.

Here’s the distinction:

📂 Table vs Partition
Table

A container for all your entities (like a database table).

You create one table per dataset (e.g., Employees, Orders).

Partition

A logical subdivision inside a table.

Defined by the PartitionKey value.

Entities with the same PartitionKey are grouped together.

Entity

A single row in the table.

Identified uniquely by PartitionKey + RowKey.

🔑 What is a Topic?
A Service Bus topic is like a queue, but instead of delivering messages to a single consumer, it fans them out to multiple subscriptions.

Each subscription behaves like a virtual queue that receives a copy of the message.

You can apply filters and actions on subscriptions so that different consumers receive different subsets of messages.

I see why it feels confusing — because in PaaS (Platform as a Service) you don’t manage servers directly, and in serverless you also don’t manage servers. The difference is subtle but important:

🔑 Why PaaS ≠ Always Serverless
PaaS: Azure manages the servers, OS, runtime, scaling, and patching for you. But your app still runs continuously on provisioned compute (e.g., Azure App Service). You’re billed for the instance/tier, even if your app is idle.

Serverless: Azure manages everything and your code runs only when triggered. There are no continuously running instances. You’re billed per execution/time, not for idle capacity.
