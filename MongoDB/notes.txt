2- acid vs base

acid vs base

In databases, ACID and BASE are two different approaches to consistency and availability.

🟢 ACID

Used mostly by relational databases like:

Microsoft SQL Server
PostgreSQL
MySQL

ACID means:

A = Atomicity → all or nothing
C = Consistency → data stays valid
I = Isolation → concurrent transactions don't interfere
D = Durability → committed data survives crashes

Example: Bank transfer

Account A -100
Account B +100

Either both happen or neither happens.

🔵 BASE

Common in distributed NoSQL systems like:

Apache Cassandra
Apache CouchDB

BASE means:

B = Basically Available
A = Soft State
E = Eventual Consistency

Idea:

Prioritize availability and scalability, even if all nodes are not immediately consistent.



3-can eventuall consistency happen in sql server 

Yes 👍

Microsoft SQL Server is an ACID database, but eventual consistency can still happen in some architectures.

The key point is:

Eventual consistency is often an architecture choice, not just a database feature.

🟢 Single SQL Server

If you have one SQL Server instance:

Application
    ↓
SQL Server

After a transaction commits:

COMMIT

everyone sees the new data immediately.

This is strong consistency, not eventual consistency.

🔵 SQL Server Replication

Example:

Primary SQL Server
        ↓
Secondary SQL Server

If replication is asynchronous:

Write to Primary
Replication happens later

A user reading from the secondary might temporarily see old data.

That's eventual consistency.

CAP theorem says that in a distributed system, you can only fully guarantee 2 out of these 3 properties at the same time:

Letter	Meaning
C	Consistency  data is written to one node , immedietly replicated to other nodes
A	Availability   replicating data across different servers  (alays get response even it is not consitent)
P	Partition Tolerance  lw noda w23t wa7ad t5osh takhod makanha
🟢 Consistency (C)

Every node sees the same data.

Example:

Node A = 100
Node B = 100
Node C = 100

After an update:

Node A = 200
Node B = 200
Node C = 200

No node returns old data.

🔵 Availability (A)

Every request gets a response.

Even if some nodes are down:

Client → Database

Database always answers.

The answer might be stale, but you get a response.

🟡 Partition Tolerance (P)

Network communication between nodes can fail.

Example:

Node A  X----X  Node B

The network link is broken.

The system continues operating despite the partition.

🟢 MongoDB Consistency, Isolation, Read Concerns, Transactions (Unified View)
1. 🧠 Core Idea (Big Picture)

MongoDB consistency model is based on:

Read Concern → how fresh/consistent data is
Write Concern → when a write is considered “safe”
Isolation → what a query can see while operations are running
Transactions → multi-document atomicity
Causal consistency → “read your own writes” ordering guarantee
🟡 2. Read Concern (Data visibility levels)

Read concern controls what version of data you are allowed to read.

🔹 1. local (default)
Reads data from the node immediately
Fastest
May read data that:
is NOT replicated yet
may later be rolled back

👉 Think:

“What this node currently has”

🔹 2. available
Same as local but even less strict in sharded edge cases
Can return:
orphaned / inconsistent shard data
Fastest but weakest consistency

👉 Think:

“Give me anything available right now”

🔹 3. majority
Reads only data that has been replicated to most nodes
What “majority reached” means:

Example (3 nodes):

Primary + S1 + S2

Majority = 2 nodes

So a write is visible only if:

at least 2 nodes have confirmed it

✔ Safe from rollback
✔ Durable after failover

👉 Think:

“Only read confirmed-safe data”

🔹 4. linearizable
Strongest consistency

Behaves like:

single database, single timeline

Reads reflect the latest confirmed write before the read starts

✔ Strongest
❌ Slowest
❌ Primary-only

🔹 5. snapshot
Provides a point-in-time view
All reads inside transaction see same snapshot

Example:

A=100, B=200 at time T1
Even if updated during query → still sees T1 state

✔ Consistent view
✔ Used in transactions
✔ Cross-shard safe snapshot

🟠 3. Write Concern (Related concept)
🔹 w:1
Write acknowledged by primary only
Fast
Can be rolled back
🔹 w:"majority"
Write acknowledged by majority of nodes
Durable
Safe from rollback

👉 Relation:

Read majority depends on write majority
🔵 4. Isolation in MongoDB (VERY IMPORTANT)

MongoDB does NOT use SQL-style isolation names internally.

Conceptual mapping only:
SQL Concept	MongoDB Equivalent
Read Uncommitted	local / default behavior
Read Committed	majority (partially)
Repeatable Read	snapshot (transactions)
Serializable	linearizable + transactions (closest approximation)
🔹 Default Isolation
MongoDB default = Read Uncommitted
Meaning:
You may see uncommitted / rolled-back data
Reads are fast, not strict
🔹 Single-document isolation
ALWAYS atomic
Never see partial update
🔹 Multi-document (without transaction)
NOT atomic
NOT consistent snapshot
Reads may see:
partial updates
mixed states
🔹 Transactions fix this

Inside transaction:

All operations behave like atomic unit
Either:
ALL commit
OR ALL rollback
🟣 5. Oplog vs Journal
🔹 Oplog (replication log)
Cluster-level
Used for replication
Primary → secondaries
Stores operations:
insert / update / delete

👉 Purpose:

“Tell other nodes what changed”

🔹 Journal
Node-level
Used for crash recovery
Ensures durability on disk

👉 Purpose:

“Don’t lose data if server crashes”

🔴 6. Causal Consistency
Meaning:

“Read your own writes in order”

Example:

Write name = "Ali"
Read name → must return "Ali"

✔ Works using sessions
✔ Requires majority read/write concern

Guarantees:
Read your writes
Monotonic reads (no going backwards)
Writes follow reads (correct ordering)

⚠ NOT a transaction
It is a session-level ordering guarantee

🟢 7. Transactions

Used when you need:

✔ Multi-document atomicity
✔ Cross-collection updates
✔ Cross-shard consistency

Behavior:
Either commit all changes
Or rollback everything
Inside transaction:
Uses snapshot-like isolation
Reads see consistent view
Writes invisible until commit
Cost:
Slower than normal operations
Should NOT replace good schema design
🟡 8. Key Differences (Very Important)
Read Concern vs Isolation
Read Concern = “what data version you read”
Isolation = “what you are protected from while reading”

👉 They are related but NOT the same thing

Causal consistency vs Transactions
Feature	Meaning
Causal consistency	ordering of operations
Transaction	atomic multi-document execution
Majority meaning (simple)
Write majority = most nodes confirm write
Read majority = read only confirmed-safe data

🚨 Connection Storms

Meaning: Sudden spike in MongoDB connections.

🔍 Causes
Bad connection pool settings (minPoolSize too low)
High traffic / load spike
Slow queries (connections stay busy)
App creates new MongoClient per request ❌
App restart → many reconnects
Sharded cluster (mongos opens many connections)
Cluster connection limit reached
🛠 Fix
Reuse one MongoClient
Tune pool (minPoolSize ≈ normal load)
Limit maxPoolSize
Scale cluster if needed

Check serverStatus:

connections.current → suddenly increases
connections.active → increases
connections.totalCreated → spikes fast
metrics.network.totalIngressTLSHandshakeTimeMillis → spikes
Logs show many “Connection accepted”



🚨 Server Selection Timeout

Meaning: Driver cannot find/connect to MongoDB server.

🔍 Causes
Firewall / network blocked (port 27017)
IP not allowed (Atlas)
DNS/SRV lookup failure
TLS/certificate issues
MongoDB server down
🛠 Fix
Open network access
Add IP to allowlist
Fix DNS / connection string
Fix TLS config
Ensure server is running
⚡ Difference
Connection Storm = too many connections
Server Timeout = no connection possible

🛠 Fix
Reuse single MongoClient (singleton)
Set proper minPoolSize ≈ maxPoolSize
Limit maxPoolSize
Scale cluster if needed
Tune mongos pools

            "directors" : { $exists: true, $ne: null, $not: {$size: 0} }

$unwind is used to split an array into multiple documents.

Suppose you have:

{
  title: "Movie A",
  directors: ["Director1", "Director2"]
}

After:

{
  $unwind: "$directors"
}

MongoDB produces:

{
  title: "Movie A",
  directors: "Director1"
}

{
  title: "Movie A",
  directors: "Director2"
}

So one document becomes multiple documents, one for each array element.

MVCC, Journal, Replication, and Read Concern are different layers.

MVCC → controls which version of data a reader sees.
Journal → crash recovery on a node.
Replication → copies data to other nodes.
Read Concern → rules about which versions are allowed to be read.
local
Read latest version on this node

Implementation:

Reader uses MVCC snapshot of the current state.
Does NOT wait for journal.
Does NOT wait for replication.
Can read data written only on primary.

Example:

Write arrives
↓
Memory updated
↓
local read can see it immediately
↓
Journal later
↓
Replication later

So:

MVCC → yes
Journal → ignored
Replication → ignored
available

Same idea as local.

Read whatever this shard currently has

Implementation:

Uses local node state.
No replication requirement.
No journal requirement.
In sharded clusters may return data even during migrations.
MVCC → yes
Journal → ignored
Replication → ignored
majority
Read only majority committed data

Implementation:

Write occurs.
Replicated to majority of nodes.
MongoDB advances majority commit point.
Reader reads snapshot at or before that commit point.

Example:

Primary
Secondary1
Secondary2

Write X
↓
Primary + Secondary1 have X
↓
Majority reached
↓
Majority read can see X

So:

MVCC → read snapshot at majority commit point
Journal → indirectly involved
Replication → REQUIRED

The key thing is:

Majority reads are based mainly on the replication commit point, not the journal.

linearizable
Show me the absolutely latest successful write

Implementation:

Read must go to primary.
MongoDB checks primary is still primary.
Read occurs after all previous majority-confirmed writes.

Example:

Write X
↓
Majority confirmed
↓
Linearizable read
↓
Must see X

So:

MVCC → yes
Journal → usually tied to majority durability
Replication → majority confirmation required
Primary only

Think:

majority = safe data
linearizable = latest safe data
snapshot
Read data exactly as it existed at time T

Implementation:

MVCC is the main mechanism here.

Example:

T1:
A=100

Transaction starts
↓
Snapshot created

Another user:
A=200

Transaction reads A
↓
Still sees A=100

MongoDB keeps older versions available through MVCC.

So:

MVCC → heavily used
Journal → not the main mechanism
Replication → only if snapshot must be majority committed
Simple Interview Answer
Read Concern	MVCC Used?	Journal Needed?	Replication Needed?
local	          Yes             	No	         No
available	      Yes	              No	         No
majority	      Yes	              No 	         Yes
linearizable	  Yes	              Indirectly	 Yes (majority)
snapshot	      Yes (main mechanism)	No	Optional, depends on transaction settings
Easy memory trick
local       = latest on this node
available   = anything available
majority    = majority replicated
linearizable= latest majority-confirmed write
snapshot    = state at a specific time

And regarding your question:

Which feature actually provides the old versions needed for reads?

MVCC provides the old versions.

The journal does not store versions for readers. The journal exists mainly so MongoDB can recover after a crash.
