10- channel.BasicQos(prefetchSize: 0, prefetchCount: 1, global: false);
🔍 What it means (simple)

👉 “Give me only 1 message at a time, and don’t send another until I ACK it.”

🔹 Parameters explained
1) prefetchSize: 0
Limit based on message size (bytes)
0 = ignore size limit
👉 Almost always left as 0
2) prefetchCount: 1
Max number of unacknowledged messages allowed per consumer

👉 1 means:

Consumer gets one message
Must ACK it before receiving the next
3) global: false
false → applies per consumer
true → applies to the whole channel

👉 Usually: false

16- topic exchange vs direct exchange   

🔹 1) Direct Exchange

👉 Routes messages based on exact match of routing key

How it works
Producer sends message with a routing key (e.g., "order.created")
Exchange delivers it only to queues bound with the same exact key
🧠 Example
Routing Key: "order.created"

Bindings:
Queue A → "order.created"   ✅ gets message
Queue B → "order.updated"   ❌ ignored
🔹 2) Topic Exchange

👉 Routes messages based on pattern matching

Uses wildcards
Much more flexible
🔹 Wildcards in topic exchange
* → matches one word
# → matches zero or more words
🧠 Example
Message:
Routing Key: "order.created.eu"
Bindings:
Queue A → "order.*"          ❌ (only 2 words expected)
Queue B → "order.#"          ✅ (matches anything after order)
Queue C → "*.created.*"      ✅ (pattern match)

18-   can a queue connect to more than one exchange

Yes — a queue can be bound to multiple exchanges, and this is a very normal pattern in RabbitMQ.

🔹 How it works

A queue doesn’t “connect” directly — it gets bound to exchanges.

👉 You can create multiple bindings like this:

channel.QueueBind("my_queue", "exchange_A", "key1");
channel.QueueBind("my_queue", "exchange_B", "key2");
🧠 What this means

Your queue will receive messages from:

exchange_A (when routing key = "key1")
exchange_B (when routing key = "key2")

if i willuse request reply pattern san i send and receive from same channel ?

Yes — you can use the same channel for both sending and receiving in a request–reply pattern in RabbitMQ.

But there are some important caveats you should understand.

🔹 Short answer
✅ Allowed: same channel for publish + consume
⚠️ Not always recommended in real systems
🔥 Why it works

A channel in RabbitMQ is just a virtual connection over a TCP connection.

👉 It can:

publish messages
consume messages
ACK/NACK

All on the same channel.

🔹 Typical request–reply flow
Client sends request:
channel.BasicPublish(exchange, routingKey, props, body);
It sets:
ReplyTo → queue name
CorrelationId → unique ID
Consumer processes and replies:
channel.BasicPublish("", props.ReplyTo, replyProps, responseBody);
Original sender listens for response on same channel

👉 This is valid

⚠️ Important limitations
1) Channels are NOT thread-safe

👉 This is the biggest issue

If you:

send request
receive reply
process concurrently

❌ You can run into race conditions

2) Blocking vs async behavior

If you:

publish
then block waiting for response

👉 you might block the same channel that needs to receive the response

3) Mixing concerns

Using one channel for:

publishing
consuming
ACKs

👉 can make debugging harder

🔥 Best practice (important)

👉 Use separate channels:

Channel 1 → send requests
Channel 2 → receive replies
🧠 Why?
Better isolation
Avoid thread-safety issues
Cleaner design
🔹 Real-world pattern
One connection
Multiple channels:
publisher channel
consumer channel
🧠 Analogy

Channel = lane in a road

One lane for sending 🚗
One lane for receiving 🚙

👉 Less traffic, fewer collisions

✅ When same channel is OK
Simple apps
Single-threaded
Learning/testing
❌ When to avoid
High throughput systems
Multi-threaded consumers
Production systems
✅ Final answer
✔ Yes, you can use the same channel
⚠️ But better to separate them in real applications
