3- why connection multiplexer open 2 tcp connection per redis server ?
Yes — by design, ConnectionMultiplexer opens two TCP connections per Redis server.
🔑 Why two connections?
Primary connection → used for normal commands (GET, SET, etc.).
Subscription connection → dedicated to Pub/Sub messaging.
Redis requires a separate connection for Pub/Sub because once a connection subscribes to channels, it can’t be used for regular commands anymore.
To avoid blocking, StackExchange.Redis automatically manages a second connection for subscriptions.

6-IConnectionMultiplexer
The IConnectionMultiplexer is responsible for maintaining all of the connections to Redis. As I described in the previous section. It routes all the commands to Redis through a single connection for interactive commands, and a separate connection for subscription, which we'll discuss more in depth later.

The IConnectionMultiplexer is responsible for exposing a simple interface to get other critical interfaces of the library. Including the IDatabase, ISubscriber, and IServer.

7-IDatabase
The IDatabase can be thought of as the primary interactive interface to Redis. It provides a single interface for your entire Redis Instance, and is the preferred interface when you are executing single commands that manipulate your application's data to Redis.
The IDatabase, unlike the IServer, abstracts the particulars of your Redis deployments away. Consequently, if you are running in a cluster and are performing a write, the IDatabase does not require you to know which server in particular you need to write to.
Also, if you have many replicas per master shard in your Cluster or Sentinel Redis deployments, the IDatabase will leverage the ConnectionMultiplexer to automatically distribute your reads across your deployment.

8-IServer
The IServer is an abstraction to a single instance of a Redis Server. You can grab an instance of an IServer by using the IConnectionMultiplexer.
GetServer command, passing in the exact endpoint information you want to retrieve.
IServer has a fundamentally different role than IDatabase as you're going to use it to handle the server level commands.
That means that in general, data modeling commands are not appropriate to be used on a server.
Rather operations like checking the server's info (the basic info of Redis), it's configuration, updating it's configuration, checking memory statistics, and the like are IServer operations.
Even scanning for the keys of a Redis server should be done at the server level



9-ISubscriber
The ISubscriber is the interface responsible for maintaining subscriptions to Redis in the pub/sub interface. Unlike the other interfaces we've looked at thus far, the subscriber does not leverage the interactive connection.
The Multiplexer explicitly opens a separate connection for subscriptions because when you subscribe to any channel on a client in Redis, the client connection converts to subscription mode.
This limits the connection to only use commands that implement subscriber functionality.
True to it's name however, the Multiplexer continues to maintain a single connection per server, and all subscriptions are handled on that single connection.
You you can get an instance of an ISubscriber by calling the IConnectionMultiplexer.GetSubscriber() method.


10-ITransaction
The ITransaction provides an interface for Redis Transactions. Transactions in Redis differ from transactions in other databases, for a full description of transactions check out the transaction section of Get Started with Redis
The ITransaction interface is fundamentally an async interface. It exposes a very similar command set to the IDatabase, but it will only expose async versions of each command. That is because each command in ITransaction is async, as they will not be competed until after Execute is called. Only after the Execute is called can the underpinning tasks for the Transaction be awaited.
You can get an instance of an ITransaction by calling IDatabase.GetTransaction() on your IDatabase object.


ITransaction in StackExchange.Redis provides a way to execute Redis transactions atomically. Unlike traditional database transactions, Redis transactions queue commands with MULTI and only execute them when EXEC is called, ensuring isolation but without rollback support.

🔑 How Redis Transactions Work
MULTI → Starts a transaction, queues commands.

EXEC → Executes all queued commands atomically.

DISCARD → Cancels the transaction, clears the queue.

WATCH → Implements optimistic locking; aborts if watched keys change.

Redis guarantees:

All commands in a transaction are executed sequentially.

No other client’s commands interleave during execution.

If EXEC is not called, nothing is applied.

⚠️ Important difference from SQL transactions: Redis does not support rollback. Once EXEC runs, all queued commands are applied.


Redis transactions: No rollback. If a command inside fails (e.g., wrong type), the others still run. 
The atomicity is about execution order and isolation, not error recovery.

-redis sintenel

what is Redis Sentinel
Redis Sentinel is a system designed to provide high availability for Redis. It monitors Redis instances, detects failures, and automatically promotes replicas to masters when needed. Think of it as the “watchdog” and “orchestrator” for Redis deployments.
🔑 Key Features of Redis Sentinel
Monitoring → Constantly checks if your master and replica instances are working.
Automatic failover → If a master goes down, Sentinel promotes a replica to master.
Notification → Alerts clients or administrators about changes in the system.
Configuration provider → Clients can query Sentinel to discover the current master, so they always connect to the right node.
⚙️ How It Works
You run multiple Sentinel processes (usually 3+ for quorum).
Sentinel monitors the master and replicas.
If the master fails, Sentinels vote to elect a replica as the new master.
Clients ask Sentinel for the current master address, ensuring they connect to the right node.
⚠️ Notes
Sentinel does not shard data — it’s only about failover and monitoring.
For large datasets, use Redis Cluster; for smaller setups needing resilience, Sentinel is often enough.
Best practice: run multiple Sentinel instances (odd number, e.g., 3 or 5) to avoid split-brain scenarios.

-pipelining

Redis pipelining is a technique that lets a client send multiple commands to the server without waiting for each individual reply.
Instead of the usual request–response cycle (send one command, wait for reply, send next),
 pipelining batches commands together, reducing network latency and improving throughput.


-EXPLICIT PIPELINING WITH IBATCH

Finally, let's explicitly pipeline all of our pings using an IBatch. An IBatch will guarantee that the client sends the entire batch to Redis in one shot, with no other commands interleaved in the pipeline. This is slightly different behavior than our implicit pipelining as in the case of implicit pipelining, commands may be interleaved with any other commands the client was executing at the time.

To explicitly pipeline these commands we'll follow a similar pattern, in this case, however, we will use the IDatabase.CreateBatch() method to create the batch, and use the batch's async methods to 'dispatch' the the tasks. It's important to note here that unlike in our implicit case, the tasks will not be truly dispatched until after the IBatch.Execute() method is called, if you try awaiting any of the tasks before then, you can accidentally deadlock your command. After calling Execute, you can then await all of the tasks.

   // clear our ping tasks list.

    pingTasks.Clear();

 

    // Batches allow you to more intentionally group together the commands that you want to send to Redis.

    // If you employee a batch, all commands in the batch will be sent to Redis in one contiguous block, with no

    // other commands from the client interleaved. Of course, if there are other clients to Redis, commands from those

    // other clients may be interleaved with your batched commands.

    var batch = db.CreateBatch();

 

    // restart stopwatch

    stopwatch.Restart();

 

    for (var i = 0; i < 1000; i++)

    {

        pingTasks.Add(batch.PingAsync());

    }

 

    batch.Execute();

    await Task.WhenAll(pingTasks);

    Console.WriteLine($"1000 batched commands took: {stopwatch.ElapsedMilliseconds}ms to execute, first result: {pingTasks[0].Result}");





-redis stream

Redis Streams are an append-only log like data structure that allows you to enqueue messages from producers to be consumed by consumers in your application. They are a powerful data structure with a rich feature set, and for a full explanation as to how and why to use Redis Streams, you can check out the Redis streams course.

In this section, we'll explore using Redis Streams in .NET using the StackExchange.Redis library. We'll learn how to:

Add Messages to a Stream.
Read Messages from a Stream.
Read Messages from a Stream in a Consumer Group.

STREAM LIMITATIONS IN STACKEXCHANGE.REDIS

Due to the multiplexed nature of StackExchange.Redis, it's important to note at the top that there is no mechanism for using the blocking paradigms available within the stream reading operations.

This means that the Stream Read operations, StreamRead & StreamReadGroup, will not be able to use the XREAD and XREADGROUP block timer or the special $ id to read only new messages.

Because StackExchange.Redis uses a multiplexed connection model (one TCP connection shared across many logical operations), it cannot safely support commands that block indefinitely.

No blocking reads → You cannot use XREAD or XREADGROUP with BLOCK.

No $ special ID for new messages only → Since blocking isn’t supported, you can’t sit and wait for new entries.

Instead, you must poll the stream periodically with StreamRead or StreamReadGroup.

 -pub/sub
 Here’s what that explanation means in simpler terms:

Redis Pub/Sub is a messaging system where publishers send messages to channels, and subscribers listen to those channels.

In StackExchange.Redis, Pub/Sub is special because it uses a separate connection from the normal one you use for commands like SET or GET.

🔑 Why a Separate Connection?
When you subscribe to a channel, Redis switches that connection into subscriber mode.

In subscriber mode, the connection can only handle Pub/Sub traffic — no normal commands.

If StackExchange.Redis tried to share the same connection for both, your normal commands would be blocked by the subscription stream.

So the library opens two connections:

Interactive connection → for normal Redis commands.

Subscriber connection → dedicated to Pub/Sub messages.

subscriber.Subscribe("news", (channel, message) =>
{
    Console.WriteLine($"Received: {message}");
}); is this line async  i mean it send and donot wait tull request and subscribption finish ?
Exactly — subscriber.Subscribe("news", …) in StackExchange.Redis is non‑blocking.

When you call Subscribe, the library sends a request to Redis to register your callback, but it doesn’t wait until Redis confirms the subscription is active.

Because the connection is multiplexed and asynchronous, the method returns right away, and the callback will only start firing once Redis has processed the subscription internally.

If you immediately publish after subscribing, there’s a race: the publish may happen before the subscription handshake completes, so the message is missed.

    -add hoc

    This hands‑on section is showing you how to use the Ad‑Hoc API in StackExchange.Redis to run commands that don’t have a dedicated wrapper in the library — and then applying it to probabilistic data structures like Bloom Filters and Top‑K.

🔑 Key Concepts
Execute / ExecuteAsync → Run any Redis command directly by name.

Arguments → Pass parameters either inline (db.ExecuteAsync("SET", "foo", "bar")) or as an object array.

Command Flags → Control behavior (e.g. demand replica, prefer master, fire‑and‑forget).

🚀 Probabilistic Data Structures
These are compact, approximate data structures useful for big datasets:

Bloom Filter → Efficiently test if an item may be in a set (false positives possible, but never false negatives).

Reserve space: BF.RESERVE

Add items: BF.MADD

Query: BF.EXISTS

Top‑K → Track the most frequent items (“heavy hitters”) in a stream.

Reserve: TOPK.RESERVE

Increment counts: TOPK.INCRBY

List results: TOPK.LIST (optionally with counts).

✅ Example Flow
Bloom Filter

csharp
await db.ExecuteAsync("BF.RESERVE", "bf", 0.01, 20000);
await db.ExecuteAsync("BF.MADD", bloomList, CommandFlags.FireAndForget);
var exists = await db.ExecuteAsync("BF.EXISTS", "bf", "the");
Console.WriteLine((int)exists); // 1 means "may exist"
Top‑K

csharp
await db.ExecuteAsync("TOPK.RESERVE", "topk", 10, 20, 10, .925);
await db.ExecuteAsync("TOPK.INCRBY", topKList, CommandFlags.FireAndForget);
var res = await db.ExecuteAsync("TOPK.LIST", "topk");
var arr = ((RedisResult[])res!).Select(x => x.ToString());
Console.WriteLine($"Top 10: {string.Join(", ", arr)}");
📊 Why It Matters
Flexibility → You can run any Redis command, even ones not wrapped in the library.

Performance → Bloom Filters and Top‑K give fast, memory‑efficient approximations.

Scalability → Useful for huge datasets where exact answers are too costly.

👉 In short: this hands‑on teaches you how to use ExecuteAsync for custom Redis commands and demonstrates it with Bloom Filters (membership tests) and Top‑K (frequency tracking).










-RedisTimeSeries — a Redis module that lets you store and query time‑tagged numeric data (like sensor readings, stock prices, or metrics). You’re using the NRedisTimeSeries extension on top of StackExchange.Redis, so the connection setup is the same, but you get extra methods for time series operations.

🔑 Flow of the Example
Create a time series → TimeSeriesCreateAsync("sensor", …) defines a key that will hold timestamped values.

Define compaction rules → You set up extra series (sensor:avg, sensor:min, sensor:max) and rules so Redis automatically aggregates the raw data every 5 seconds.

Produce data → A background task adds a random integer every second with TimeSeriesAddAsync("sensor", "*", value).

Consume raw data → Another task fetches the latest reading each second using TimeSeriesGetAsync.

Consume aggregated data → A task runs every 5 seconds, querying the compacted series with TimeSeriesMGetAsync and printing averages, mins, and maxes.

Run until keypress → Console.ReadKey() keeps the producer and consumers alive until you stop them.

📊 Why This Matters
Scalability → You can handle continuous streams of data efficiently.

Aggregation → Redis does the heavy lifting of computing averages/min/max, so your app doesn’t need to.

Flexibility → Labels let you filter and query multiple series at once.

Decorates the class you want to store in Redis (Employee, Sale).

Marks the property that will serve as the unique ID.

Typically applied to Id in your model.

IndexedAttribute

Marks fields you want to query or sort on.

Works on strings, numbers, enums, GeoLoc, and even nested classes.

SearchableAttribute

Enables full‑text search on string fields.

Queries like == in LINQ become full‑text matches instead of exact string equality.

Useful for fields like Name or Address.
